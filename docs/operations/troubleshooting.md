# Troubleshooting

Common failures in an OCSO deployment, with the exact error codes and log lines the code produces and what
to do about each. For operators and Tech admins. Deployment-specific tables are also in
[Docker Compose](../guides/deploy/docker-compose.md#troubleshooting) and
[AWS](../guides/deploy/aws.md#troubleshooting).

## Reading an error

Every API error has the same shape, and the log line for it carries the same `correlationId`:

```json
{ "error": { "category": "conflict", "code": "approval_required", "message": "…", "details": { }, "correlationId": "…" } }
```

| Category | HTTP status |
|---|---|
| `validation` | 400 |
| `authentication` | 401 |
| `authorization`, `policy_denied` | 403 |
| `not_found` | 404 |
| `conflict` | 409 |
| `tool_rejected` | 422 |
| `provider_rate_limited` | 429 |
| `internal` | 500 |
| `provider_unavailable`, `tool_unavailable` | 502 |
| `capacity` | 503 |
| `timeout` | 504 |

Unexpected errors become `internal` with a generic message; the detail is only in the server log.
Secret values are never included in errors or logs.

## Start-up and configuration

The api and worker validate their whole configuration before they start and print every problem at once:

```text
Invalid OCSO configuration:
  - BETTER_AUTH_SECRET (≥ 32 chars) is required in production (Compose: generated by keygen)
  - DATABASE_URL: Invalid url (value hidden)
```

| Message | Fix |
|---|---|
| `<VAR>: … (value hidden)` | The variable is malformed. Secret-looking names (`KEY`, `SECRET`, `TOKEN`, `PASSWORD`, database URLs) never have their value printed. |
| `<SETTING>=<name> is not available; registered <noun> drivers: …` | A `*_DRIVER` value names a driver no installed plugin registers. Use one of the listed names, or install the plugin (`OCSO_PLUGINS`). |
| `BETTER_AUTH_SECRET (≥ 32 chars) is required in production` | Compose generates it; on AWS it is not wired yet ([AWS gaps](../guides/deploy/aws.md#2-close-the-known-gaps-first)). |
| `AUDIT_SIGNING_KEY_FILE (…) or AUDIT_SIGNING_KEY is required in production` | Provide the Ed25519 key. Compose: `docker compose up keygen`. |
| `AUDIT_DRIVER=postgres requires AUDIT_DATABASE_URL (or AUDIT_DATABASE_URL_FILE)` | The process has no audit store URL. |
| `EMAIL_DRIVER is required in production: …` | Configure email ([Email](../guides/email.md)), or set `EMAIL_ALLOW_LOG_IN_PRODUCTION=true` for a trial. |
| `OCSO_ENABLE_DEV_PROVIDERS must be false in production` | The scripted model is for development. Remove it, or add `OCSO_ALLOW_DEV_PROVIDERS_IN_PRODUCTION=true` for a demo only. |
| `OCSO_DEV_SKIP_ACCESS_APPROVAL must be off in production` / `OCSO_ENABLE_TEST_HOOKS must be off in production` | Test-only settings leaked into production. Remove them. |
| `SECRETS_DRIVER=local requires OCSO_SECRETS_MASTER_KEY or OCSO_SECRETS_MASTER_KEY_FILE` | The master key is missing. On Compose, check that the `secrets` volume is mounted. |
| `QUEUE_DRIVER=sqs requires SQS_QUEUE_URLS and AWS_REGION` | AWS environment incomplete. |
| `ocso-entrypoint: <VAR>_FILE points to a missing or unreadable file` (exit 66) | Compose: a secret file is missing. Run `docker compose up keygen`; for `RESEND_API_KEY_FILE` or `SMTP_PASSWORD_FILE`, write the file first. |
| `no SQS queue configured for topic <topic>` | `SQS_QUEUE_URLS` lacks a topic. On the current Terraform, add `conversation.route` to `queue_topics`. |

## Migrations

Read the logs first: `docker compose logs migrate`, or `aws logs tail <migrate_log_group>` on AWS. Both
steps print JSON lines; the last one says what failed.

| Message | Cause and fix |
|---|---|
| `DATABASE_URL is required` (exit 2) | The migrate step has no database URL. |
| `migration NNNN_name.sql was modified after being applied` | An already-applied file changed. Restore the original file. Never edit a committed migration; fix forward with a new one. |
| `migration NNNN_name.sql failed: <reason>` | The SQL failed; that file's transaction rolled back and later files did not run. Fix the cause (often data a constraint rejects) and run `migrate` again. |
| `audit-migrate (postgres) needs AUDIT_DATABASE_OWNER_URL and AUDIT_DATABASE_URL` | The audit step has no owner or writer URL. |
| `audit role <role> does not exist: create it, or set AUDIT_PROVISION_ROLE=true` | `AUDIT_PROVISION_ROLE=false` but the DBA has not created the role. |
| `… Refusing in production; set AUDIT_ALLOW_OWNER_WRITER=true to accept it` | The writer URL uses the audit database owner, so append-only is not enforced. Use a separate writer role. |
| `AUDIT_MIN_RETENTION_DAYS must be an integer of at least 365` | Raise it. |
| `audit migration <file> was modified after being applied` | Same rule as the main migrations, for the audit store (ClickHouse). |
| `AUDIT_DRIVER=<name> has no provisioning here; drivers: …` | The audit driver name is wrong. |

The api and worker wait for `migrate` to exit 0 on Compose, so a failed migration leaves them not started.
On AWS, do not roll the services until the migrate task exits 0. See [Upgrades](upgrades.md).

## First-run setup

| What you see | Fix |
|---|---|
| **The OCSO API is not reachable.** on `/setup` | The web app cannot reach the api at `API_URL`. Check the api's health and logs. |
| `invalid_setup_token` (401) | The token does not match. Compose: `docker compose logs api \| grep "setup token"`. From source without `OCSO_SETUP_TOKEN`, a new token is generated on every api start. |
| Setup works on one attempt and fails on the next (AWS) | The api tasks must share one `OCSO_SETUP_TOKEN` from the bootstrap secret. |
| `setup_already_completed` (409), or `/setup` redirects to `/login` | A user exists already. Sign in. |
| `weak_password` | The password must be at least 12 characters and pass the policy shown. |

## Sign-in, MFA and SSO

| What you see | Cause and fix |
|---|---|
| Sign-in page loads but sign-in fails on a remote host over plain http | The session cookie is `Secure`. Use TLS, or `SESSION_COOKIE_SECURE=false` for a trial only. |
| `too_many_attempts` (401) | Sign-in throttling. Wait. Behind a proxy, check `OCSO_TRUSTED_PROXY_HOPS` so users are not throttled as one address. |
| `mfa_enrollment_required` (403) | The user's role requires MFA (**Settings → Sign-in security → Require MFA for roles**). They must enrol before doing anything else. |
| **Single sign-on did not complete.** on the sign-in page | The IdP refused, or the user is unknown and the provider does not auto-provision. Invite the user, or turn on auto-provision for that provider. |
| `sso_discovery_failed` when saving an OIDC provider | OCSO could not fetch the issuer's discovery document. Check the issuer URL. An IdP on a private network must be listed in `OCSO_AUTH_TRUSTED_ORIGINS` and reachable from the api. |
| `sso_provider_rejected` | The SSO configuration was rejected; the message says why. |
| `last_password_admin` (409) | At least one active Tech admin must keep password sign-in. Add or enable another first. |
| Every Tech admin is locked out | Break-glass: set `OCSO_RECOVERY_TOKEN` (32+ random characters) on the api, restart it, open `/recover`, reset one Tech admin's password, then remove the variable. Each token value works once and the use is audited. |
| Everyone was signed out and authenticator codes stopped working | `BETTER_AUTH_SECRET` changed. Restore the previous value from the `secrets` backup, or have users enrol again. |

See [Sign-in](../guides/sign-in.md).

## Approvals

| Code | Meaning and fix |
|---|---|
| `approval_required` (409) | The change must be a proposal. Name a checker and a reason (**Submit for approval**). |
| `checker_not_eligible` | You named yourself, or the person whose access changes. Name a colleague who holds the check permission. |
| `bootstrap_not_allowed` | Another eligible checker exists, so you cannot approve your own change. |
| `content_changed` | The object changed after the proposal was submitted. The maker edits and resubmits. |
| **The named checker can no longer approve this** | The checker lost the permission or was disabled. Reassign the proposal. |

## Channels, routing and web chat

| What you see | Cause and fix |
|---|---|
| Customer messages get no reply; the api logs `customer message rejected (no_router): channel <name> has no active router` | Attach and activate a router for the channel. The same reason with `router <name> has no queue with an agent to route to` means the router's queues have no approved agent. |
| The api logs `channel webhook: customer messages rejected` with `reasons` | The webhook arrived but the messages could not be admitted. The reasons say why (for example `no_router`). |
| `webhook_signature_invalid` (401/403) on `/channels/<kind>/<key>/webhook` | The provider's signature did not verify. Twilio signs the exact URL: `OCSO_PUBLIC_URL` plus the path must match the URL configured in Twilio, with no trailing slash. Meta: the app secret is wrong. Slack and Teams: the signing secret or bot credentials do not match the channel. |
| Provider webhooks return 404 | Only `/channels`, `/public`, `/oauth`, `/.well-known` and `/blobs` are proxied to the api. Use the webhook URL the channel dialog shows. |
| `webchat_origin_not_allowed` (403) | The site embedding the widget is not in the channel's allowed origins. |
| `rate_limited` (429, with `Retry-After`) on web chat | Per-address or per-visitor limits. Many visitors behind one NAT share the per-address session limit: raise it with `OCSO_WEBCHAT_RATE_LIMITS=session=300` on the api. |
| `queue_not_approved` | A transfer or route targets a queue that is not approved yet. |

See [Channels](../guides/channels/README.md) and [Routing](../concepts/routing.md).

## Audit store incidents

The worker leader ships audit events from the main database to the audit store and seals them into a hash
chain. When something goes wrong it opens an incident, shown on **Platform → System → Audit store** and on
**Exceptions**. OCSO keeps working: events wait in the main database, and the audit screen serves the
local copy. `/health/ready` does not depend on the store; `/health/dependencies` reports it.

| Incident | Meaning | What to do |
|---|---|---|
| `STORE_DOWN` (**The audit store is not answering**) | The store did not answer. Shipping backs off and retries. | Check the audit database (`docker compose ps audit-db`, or the RDS instance), its credentials and network. The incident resolves when the store answers. |
| `SHIP_FAILED` | The store answered but rejected the write. | Check the worker log for the reason; usually permissions of the writer role. Run `migrate` again to re-apply grants. |
| `RECONCILE_MISSING` | Events the store had confirmed were missing and were re-sent. | Usually after an audit store restore. Watch **Shipping** return to zero and verify the chain. |
| `EXPORT_FAILED` | The daily signed export failed or was blocked. | Check blob storage, and whether an open `CHAIN_BROKEN` or `SIGNING_KEY_CHANGED` blocks it. |
| `CHAIN_BROKEN` | The hash chain did not verify over a range of positions. | Investigate with `audit-verify --from <first> --to <last>`, then **Acknowledge break** (needs `audit.verify`) with a note. Nothing in the store is rewritten. |
| `SIGNING_KEY_CHANGED` | Checkpoints were signed by a key this deployment does not trust. | Usually a lost `secrets` volume. Restore the old signing key, or add its public key to `AUDIT_TRUSTED_PUBLIC_KEYS_FILE` (Compose) or `audit_trusted_public_keys` (AWS) after a deliberate rotation. |

Every store call is bounded by `AUDIT_STORE_TIMEOUT_MS` (default 15 s). See [Audit](../concepts/audit.md) and
[Backups and restore](backups-and-restore.md#restoring-only-the-audit-store).

## Workers and scaling

| What you see | Cause and fix |
|---|---|
| Worker replicas keep restarting | `docker compose logs worker`. Check the configuration errors above and that `DATABASE_POOL_SIZE` × (api + workers) stays below PostgreSQL's `max_connections`. |
| Scaling status `FAILED` or stuck `PENDING` | See [Worker scaling](worker-scaling.md#troubleshooting). |
| Replies are slow and the *queue age above threshold* alert fires | Not enough worker slots. Add replicas (Compose) or raise **Max workers** (ECS). |

## Model providers

| Code | Meaning |
|---|---|
| `provider_credentials_invalid` | The credentials are missing or have unknown fields for that provider. |
| `all_targets_failed` (502) | The primary model and every fallback in the profile failed. Check **Platform → System** provider health. |
| `provider_concurrency_exhausted` (503) | The provider's concurrency limit in OCSO is used up. |
| `model_target_not_permitted` (403) | The profile's target breaks the deployment policy (allowlist, residency, cross-provider or cross-region fallback). |

## Email

| What you see | Fix |
|---|---|
| **Settings → Email** warns that email is not delivered | `EMAIL_DRIVER` is unset or `log`. Configure Resend or SMTP. |
| **Send test email** fails with `auth` | Resend: the sender domain is not verified, or the key is revoked or restricted to another domain. SMTP: wrong user or password, or TLS failed. |
| `invites_unavailable` / `email_unavailable` | No email sender is available in this deployment. |
